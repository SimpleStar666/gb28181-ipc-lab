# 09 音画同步原理

> **一句话**：GB28181 里音画同步的依据就是 PS 容器里的 PTS ——
> 视频和音频用同一个 90kHz 时钟，接收端只要按 PTS 播放就自动对齐。
>
> **这一章直接对应 JD 里"音画不同步怎么排查"那条。**

---

## ① 这一步解决什么问题

音画不同步有两种：**音频领先视频**、**视频领先音频**。
表现为口型对不上、或者敲击声和画面差半秒。

要解决它，先得回答一个更基本的问题：
**接收端凭什么知道"这一帧画面"和"这段声音"是同一时刻的？**

两条技术路线：

| 路线 | 代表 | 同步依据 |
|---|---|---|
| **共享时间基** | **GB28181 / MPEG-PS** | 音视频 PTS 来自同一个 90kHz 系统时钟 |
| 独立时间基 + 对时 | WebRTC / RTP | 各自的时间戳 + RTCP SR 把 RTP 时间戳映射到 NTP 墙上时钟 |

**GB28181 走的是第一条。这是 PS 容器存在的最核心理由。**

---

## ② 协议长什么样

### 共享时间基长什么样

```
        90kHz 系统时钟（唯一的）
  0 ──────── 6000 ──────── 12000 ──────── 18000 ────────►
  │           │             │              │
视频 PES   视频帧1        视频帧2        视频帧3         每帧 +6000
           PTS=6000      PTS=12000      PTS=18000
           │        │          │         │
音频 PES   ├─1800─┤─1800─┤─1800─┤─1800─┤ ...            每帧 +1800
           音频1  音频2  音频3  音频4

时间换算：6000 / 90000 = 66.7ms     1800 / 90000 = 20ms
```

**所有 PES 包的 PTS 都在这条轴上。** 接收端解析 PS 时，
把视频帧按 PTS 放到时间轴上的位置，把音频帧也放上去，
然后按这条轴播放 —— 自动对齐。

**不需要 RTCP、不需要 NTP 对时、不需要额外的同步信令。**

### 对比 WebRTC 需要多做什么

WebRTC 里视频和音频是**两路独立的 RTP 流**，各有自己的时间戳起点和频率：

```
视频 RTP: ts 基于 90kHz，起点随机
音频 RTP: ts 基于 48kHz，起点随机（且和视频起点无关）
```

要用它们同步，必须额外做：

1. **RTCP SR（Sender Report）**：发送端周期性发这个报文，
   里面同时包含"NTP 墙上时钟"和"对应的 RTP 时间戳"
2. **接收端换算**：用 SR 做两路 RTP 时间戳 → NTP 的映射
3. **选主时钟**：通常音频当主时钟（音频对抖动更敏感，不能随便变速）
4. **同步播放**：视频等音频，或者丢帧追上

**这就是"共享时间基"省下来的工作量。**

## ③ 为什么会不同步（四种原因）

既然时间基是共享的，那不同步只能来自四个地方：

### 原因一：PTS 本身算错了

最直接的原因。**本项目抓出的那个 bug 就属于这一类**：
PTS 第 3 字节右移了一位，编码出来的 PTS 与真实值不符。

危险的是**这种错不一定表现为不同步** ——
如果下游用 RTP 时间戳而不是 PES PTS 来定时，画面照样正常。
所以必须主动验证（见 ⑤）。

### 原因二：音频 PTS 用了错误的时钟域

音频采样率是 8000 Hz，**但 PTS 必须在 90000 Hz 域**。

```c
/* ✗ 错：拿采样率当时钟 */
audio_pts += 160;

/* ✓ 对：换算到 90kHz */
audio_pts += 90000 * 20 / 1000;   /* = 1800 */
```

错误后果：音频 PTS 增长速度只有正确的 8/90，音频会被严重拖慢。

### 原因三：首帧的对齐基准不同

如果视频第一个 PTS 是 0，音频第一个 PTS 是 9000（差了 0.1 秒），
那整体就差了 0.1 秒。**两个流的起始 PTS 必须对齐到同一个时刻。**

真实设备上的做法：音视频采集共用同一个系统时钟源，
编码器出帧时打的 PTS 天然同源。

### 原因四：网络抖动导致播放端调度失衡

PTS 是对的，但网络抖动让音频包晚到，
播放端如果"谁到了就播谁"，就会出现瞬时不同步。

对策是**抖动缓冲（jitter buffer）**：先把包按 PTS 排队，
攒够一小段（比如 100ms）再按时间轴吐给解码器。
代价是增加延迟，收益是吸收抖动。

> 注意区分：**原因一到三是"数据错了"，原因四是"调度问题"。**
> 排查顺序永远是先排除数据错，再看调度 —— 因为数据错可以离线验证，
> 调度问题依赖实时环境，难复现。

## ④ 代码怎么长出来的

### 视频 PTS

```c
unsigned long long pts = 0;
...
send_rtp_packet(ps, ps_len, &seq, (unsigned int)(pts & 0xFFFFFFFF));
pts = (pts + GB_VIDEO_PTS_STEP) & GB_PTS_MASK;   /* +6000 */
```

### 音频 PTS

```c
typedef struct {
    uint64_t pts90k;
    uint32_t phase;
    int      freq_hz;
} gb_audio_gen_t;

int gb_audio_gen_next(gb_audio_gen_t *g, uint8_t *out, size_t cap, uint64_t *pts90k)
{
    /* 生成 160 个 int16 正弦样本 → A-law 编码 → 160 字节 */
    ...
    *pts90k = g->pts90k;
    g->pts90k = (g->pts90k + GB_AUDIO_PTS_STEP) & GB_PTS_MASK;   /* +1800 */
    return GB_AUDIO_FRAME_LEN;
}
```

**关键：音频生成器也要从 0 开始累加 90kHz 的 PTS，和视频同源。**
不能用自己的采样计数。

### 复用输出：按 PTS 排序

```c
while (gb_push_running(ctx)) {
    if (audio_on && ctx->next_audio_pts <= ctx->next_video_pts) {
        /* 发音频 */
        gb_audio_gen_next(&gen, abuf, sizeof(abuf), &apts);
        gb_ps_pack_audio(psbuf, sizeof(psbuf), abuf, n, apts);
        gb_rtp_send_ps(fd, dst, dstlen, &tx, psbuf, pslen);
        ctx->next_audio_pts += GB_AUDIO_PTS_STEP;
    } else {
        /* 发视频 */
        int n = gb_src_next_frame(src, &frame, &flen);
        if (n > 0) {
            gb_ps_pack_video(psbuf, sizeof(psbuf), frame, flen,
                             ctx->next_video_pts, psm, psm_len);
            gb_rtp_send_ps(fd, dst, dstlen, &tx, psbuf, pslen);
            ctx->next_video_pts += GB_VIDEO_PTS_STEP;
        }
    }
}
```

**按 PTS 大小决定发谁** —— 这样输出的 PES 顺序就是显示顺序。
（真实设备上这一层通常由 SoC 的复用器或编码器框架统一调度，
但原理一样：谁的时间戳小谁先出。）

## ⑤ 怎么验证音画同步

### 数据层验证（离线，最强）

**验证一：PTS 位域往返**

```bash
bash tools/selftest.sh        # test_pts.c 会做 33 位往返解码校验
```

自己写个解码函数按位域表还原 PTS，断言解出来的等于输入。
**这一条能抓住所有位域错误**，包括原项目那个潜伏很久的 bug。

**验证二：用 ffprobe 反读**

```bash
bash tools/verify_pts.sh
```

打一个 PTS 已知的 `.ps`，用 `ffprobe -show_packets` 读回来比对。
**这是唯一能证明"我编码出去的东西，标准工具也能读对"的手段。**

**验证三：音视频 PTS 落在同一时间轴**

从 dump 出来的 PS 里把视频 PES 和音频 PES 的 PTS 都提取出来，
按顺序打印，人工确认它们是交错的、并且音频步进 1800、视频步进 6000：

```
video  pts=0       (0.000s)
audio  pts=0       (0.000s)
audio  pts=1800    (0.020s)
audio  pts=3600    (0.040s)
audio  pts=5400    (0.060s)
video  pts=6000    (0.067s)   ← 第 2 帧视频
audio  pts=7200    (0.080s)
...
```

**这张表打印出来，音画同步就是"看得见"的。**

### 感知层验证（在线）

```bash
ffplay -autoexit -t 20 -rtsp_transport tcp "rtsp://127.0.0.1:554/rtp/<stream>"
```

用**有节奏感的内容**测（比如每秒一次的滴答声 + 同步闪屏），
比正弦波更容易听/看出偏移。

## ⑥ 排查顺序（遇到"音画不同步"照这个走）

```
第 1 步：确认 PTS 编码对不对（离线）
        → 往返解码校验 + ffprobe 反读
        → 不对：改代码。对了：往下

第 2 步：确认音频 PTS 用的是 90kHz 域（离线）
        → 打印音频 PTS 序列，步进应该是 1800
        → 是 160 或 1024 之类：改代码

第 3 步：确认音视频起始 PTS 对齐（离线）
        → 两个流的第一个 PTS 应该都在 0 附近

第 4 步：确认 PES 输出顺序与 PTS 顺序一致（离线）
        → 按 PTS 排序输出

第 5 步（以上都对才开始查这个）：抖动缓冲
        → 播放端有没有按 PTS 排队
        → 抖动缓冲深度够不够
```

**为什么这个顺序重要？** 因为前四步都可以离线验证、可以复现，
第五步依赖实时环境、很难复现。
**先排除确定性因素，再查非确定性因素** —— 这是排障的通用原则。

## ⑦ 常见坑

| 坑 | 现象 | 属于哪类原因 |
|---|---|---|
| PTS 位域错一位 | 不一定表现出来（下游可能用 RTP ts） | 原因一 |
| 音频 PTS 加了 160 而不是 1800 | 声音越来越慢 | 原因二 |
| 音频 PTS 直接用采样计数 | 同上 | 原因二 |
| 音视频起始 PTS 不同 | 整体固定偏移 | 原因三 |
| RTP timestamp 与 PES PTS 不同源 | 帧序错乱（原项目踩过） | 原因三 |
| 无抖动缓冲 | 网络一抖就瞬时不同步 | 原因四 |
| 音频包每帧也带 PSM | 带宽浪费（不是同步问题但会被问） | — |

## ⑧ 面试怎么答

**问：GB28181 的音画同步是怎么实现的？**

> "靠 PS 容器里共享的时间基。视频和音频的 PES 都带 33 位 PTS，
> 而且这些 PTS 来自同一个 90kHz 系统时钟 ——
> 视频每帧递增 6000（15fps），音频每帧递增 1800（20ms 一帧）。
> 接收端解析 PS 就同时拿到了两路的时间轴，按 PTS 播放自动对齐，
> 不需要 RTCP，也不需要 NTP 对时。
>
> 对比 WebRTC 是两路独立 RTP，各有自己的时间戳起点和频率，
> 必须靠 RTCP Sender Report 把 RTP 时间戳映射到 NTP 墙上时钟才能同步。
> 这是 PS 容器最大的价值。"

**追问：那如果不同步了，你怎么查？**
→ 用第六节的五步顺序答。重点说清：
   "前四步都是确定性的，可以离线复现 —— 先查 PTS 编码、再查音频时钟域、
   再查起始对齐、再查输出顺序。这些都对了才去查抖动缓冲，
   因为那个依赖实时环境、难复现。"

**追问：你们实际遇到过同步问题吗？**
→ 讲 PTS 位域那个 bug，并强调最有价值的一点：
   "那个 bug 的表现不是'不同步'，而是**完全看不出来** ——
   因为下游平台多数路径用 RTP 时间戳而不是 PES PTS 来定时，画面正常。
   我们是用 33 位往返解码校验 + ffprobe 反读 PTS 才发现编码值对不上。
   这让我意识到'画面正常'和'协议正确'是两件事。"
   ← **这是本章最值钱的回答**，它同时展示了：会写测试、懂验证方法论、
      不迷信"能跑就行"。

**追问：抖动缓冲是什么？**
→ "接收端先把包按 PTS 排队，攒够一小段再按时间轴吐给解码器。
   代价是增加延迟，收益是吸收网络抖动。
   一般 50 到 200 毫秒，要跟延迟预算权衡。
   注意它解决的是'调度'问题，不是'数据'问题 ——
   PTS 本身错了，缓冲再大也没用。"
