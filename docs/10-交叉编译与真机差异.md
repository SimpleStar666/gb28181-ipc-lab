# 10 交叉编译与真机差异

> **一句话**：交叉编译只是"用 x86 工具链产出 ARM 二进制"，
> 难的不是编译，是**证明它真的能跑**，以及**说清它和真机的差距在哪**。

---

## ① 这一步解决什么问题

前九章的代码是在开发机（x86）上跑通的。但 IPC 设备的 CPU 是 ARM：
海思 Hi3516、瑞芯微 RV1106、星宸 SSC338 等等。

你要把同一份 C 源码，编译成能在目标板子上跑的二进制。这一步叫交叉编译。

**"交叉"的意思是**：编译它的机器（x86）和运行它的机器（ARM）不是同一个架构。
编译器本身跑在 x86 上，但它产出 ARM 机器码。

---

## ② 命令长什么样

```bash
aarch64-linux-gnu-gcc -static -O2 -pthread \
    -o build/gb28181_device_aarch64 \
    src/*.c
```

**逐参数解释**：

| 参数 | 作用 | 为什么需要 |
|---|---|---|
| `aarch64-linux-gnu-gcc` | 交叉编译器前缀 | 告诉 gcc 输出 ARM64 而不是 x86 |
| `-static` | 静态链接 | **嵌入式默认选择**，见下 |
| `-O2` | 优化等级 2 | 嵌入式资源紧张，不能不带优化 |
| `-pthread` | 链接 pthread | 推流线程和心跳线程需要 |

### 为什么 `-static` 是嵌入式默认选择

动态链接的程序运行时要去目标板上找 `.so` 文件。
目标板的根文件系统（rootfs）通常**和你开发机的 glibc 版本对不上**，
甚至可能根本没有完整的 glibc。

现象是：程序在开发机上跑得好好的，拷到板子上报
`No such file or directory` —— 而这个错误看起来像是"文件不存在"，
实际上是**动态链接器找不到**。

`-static` 把所有依赖打进一个二进制，代价是体积大（本项目约 1.2 MB），
收益是"拷过去就能跑"。

### 验证产物架构

```bash
file build/gb28181_device_aarch64
# 期望：ELF 64-bit LSB executable, ARM aarch64, statically linked
```

**`aarch64` 这三个字必须出现。** 如果显示 `x86-64`，说明编译器选错了，
后面所有调试都是在错误的前提下进行的。

---

## ③ 怎么在 x86 上跑 ARM 二进制：QEMU

编译出来了，但手上没有 ARM 板子。怎么办？

**QEMU 用户态模拟（`qemu-aarch64`）**：把 ARM 指令一条条翻译成 x86 执行，
但 **syscall 直接透传给宿主 Linux 内核**。

```bash
qemu-aarch64 ./build/gb28181_device_aarch64 -c config.ini
```

### 用户态模拟 vs 系统态模拟

这两个概念必须分清，面试会问：

| | 用户态模拟（`qemu-aarch64`） | 系统态模拟（`qemu-system-aarch64`） |
|---|---|---|
| 模拟什么 | 只有 CPU 指令 | 整个机器：CPU、内存、外设、中断 |
| 内核 | **用宿主内核** | 跑一个完整的客户机内核 |
| 网络 | **和宿主一致**（同一套 socket） | 需要虚拟网卡配置 |
| 速度 | 快 | 慢很多 |
| 用途 | 验证"程序逻辑对不对" | 验证"内核驱动、启动流程" |

**本项目用用户态模拟**，因为要验证的是"软件栈逻辑"（SIP 信令、PS 打包、RTP 时序），
这些全在用户态，和内核/外设无关。

**关键收益：UDP 网络行为和真机完全一致。**
因为你用的是宿主的 socket 栈，`sendto()` 出去的就是真的 UDP 包，
平台收到的和你从 x86 版本发出的一模一样。

### QEMU 验证的边界在哪

这一条**面试必问**，必须说得清楚：

| 验证到了 | 没验证 |
|---|---|
| 交叉编译产物能在 ARM 上正确执行 | 硬件外设（摄像头、音频编解码器、GPIO） |
| 指令集执行正确（不会有 x86 特有的未定义行为） | 中断处理、驱动 |
| 完整协议栈：SIP 信令、PS 打包、RTP 时序 | 硬件编码器（VENC/MPP）的调用 |
| 静态链接产物无缺失依赖 | 真机的内存/带宽约束 |
| 字节序、对齐等架构相关问题 | 长时间的稳定性（温度、内存泄漏） |

**判断口径**：
> QEMU 用户态模拟验证的是 **指令集执行正确性 + 交叉编译产物的可运行性**。
> GB28181 全链逻辑在用户态完整真实执行，与真机 IPC 固件场景等价的是这部分软件栈。

## ④ 一个很有价值的验证方法：双架构对照

原项目做了一件很有说服力的事：**同一份源码，x86 原生编译和 aarch64 交叉编译都跑一遍全链**。

```
源码 ──┬── x86 原生编译 ──► 全链通过 ✅
       │
       └── aarch64 交叉编译 ──► qemu 运行 ──► 全链通过 ✅
```

**这一步排除了"架构差异导致的问题"。** 如果 x86 通过而 aarch64 失败，
问题一定在架构相关的地方（字节序、对齐、类型宽度）；
如果两个都通过，说明逻辑本身没问题。

**这个"对照组"的思路比单跑一次有价值得多**，面试时值得主动提。

## ⑤ 真机上会有什么不同

假设你现在拿到一块真实的 IPC 板子（比如瑞芯微 RV1106 或海思 Hi3516），
这份代码要改哪里？

### 差别一：码流来源

```c
/* 本项目 */
int gb_src_next_frame(...) {
    fread(stream_buf + stream_used, 1, 65536, fp);   /* 从 FIFO 读 */
}

/* 真机（海思示例） */
int gb_src_next_frame(...) {
    HI_MPI_VENC_GetStream(ve_chn, &stream, HI_TRUE);  /* 从 VENC 通道取 */
    /* stream 里有虚拟地址、物理地址、长度、PTS */
    HI_MPI_VENC_ReleaseStream(ve_chn, &stream);       /* 用完必须释放 */
}
```

**要注意的点**：
- VENC 出流是"取-用-还"的三段式，**必须配对释放**，否则编码器缓冲区会耗尽
- 出流接口通常一次给一个完整帧（或一个 NAL），不需要你自己做 AnnexB 切分
- PTS 一般由编码器直接给出（基于硬件时钟），比你自己累加更准

### 差别二：RTP 发送可能走零拷贝

真机上为了省内存带宽，常用 VB（Video Buffer）池 + 物理地址直传：

```c
/* 海思典型流程 */
HI_MPI_VB_SetConf(...);            /* 配置视频缓冲池 */
HI_MPI_VB_Init();
HI_MPI_SYS_Bind(&src_chn, &dst_chn);  /* 用 bind 代替手工拷数据 */
```

PS 封装这一层通常还是要自己写（SoC 不代劳），
但可以拿物理地址直接喂给网卡驱动，避免 memcpy。

### 差别三：硬件编码器替代 libx264

```bash
# 本项目（开发机）
ffmpeg -c:v libx264 ...

# 真机
# 直接调 SoC 的 VENC，没有 ffmpeg
```

**编码参数的含义不变**（GOP、码率、帧率），但**接口完全不同**。
好消息是：应用层只看到"码流"，编码器怎么来的它不关心 —— 这正是本项目分层设计的价值。

### 差别四：没有 FIFO，没有 rootfs 里的 ffmpeg

本项目用 FIFO 是因为 WSL 里没法调真机的编码器。
真机上直接调 SDK，不需要 FIFO 这个中间层。

**但 FIFO 这一步的教学价值在于**：它强制你实现"流式读 + 滚动缓冲 + 锚定 SPS"，
而这套逻辑在真机上照样需要（VENC 出流也可能跨缓冲区边界）。

## ⑥ 常见坑

| 坑 | 现象 | 定位 |
|---|---|---|
| 忘了 `-static` | 板子上报 `No such file or directory` | `file` 看是否 dynamically linked |
| 编译器前缀写错（用了 `gcc` 而不是交叉版） | `file` 显示 x86-64 | 一定 `file` 验证一次 |
| `-pthread` 漏了 | 链接报 `undefined reference to pthread_create` | — |
| `qemu-aarch64` 没装 | `command not found` | `apt install qemu-user` |
| 交叉编译时 `\| head` 导致 SIGPIPE | **编译产物没更新，还是旧二进制** | 别用管道，或重定向 stderr 到文件 |
| 目标板 glibc 版本比开发机新 | 运行时 `GLIBC_2.xx not found` | 用 `-static`，或用目标板配套工具链 |
| QEMU 下性能差以为是代码问题 | 推流卡顿 | 动态翻译 + 软编码 + USB 透传的叠加代价，不是链路问题 |

### 那个 SIGPIPE 坑值得单独说

原项目踩过：`gcc ... 2>&1 | head -30`。
**`head` 读满 30 行就退出，gcc 再往 stderr 写就被 SIGPIPE 杀掉**，
编译中断，产物还是上一次的旧二进制。

于是你改了代码、编译"成功"、运行结果没变 —— 会怀疑人生。

**对策**：不要用管道；需要看输出就重定向到文件。

## ⑦ 面试怎么答

**问：你有嵌入式交叉编译经验吗？**

> "有。用的 `aarch64-linux-gnu-gcc`，静态链接。
> 选静态是因为目标板 rootfs 的 glibc 版本通常和开发机不一致，
> 动态链接到板子上会报 `No such file or directory` —— 看着像文件不存在，
> 其实是动态链接器找不到。
> 编译完一定用 `file` 确认一下是 `ELF 64-bit LSB executable, ARM aarch64`。
> 没有真机的时候用 QEMU 用户态模拟跑，syscall 透传宿主内核，
> UDP 网络行为和真机一致。"

**追问：QEMU 跑出来的结果能算真机经验吗？**
→ **这个问题一定要诚实回答，而且要答得有分寸**：
   "不算完整的真机经验，但有明确的价值边界。
   用户态 QEMU 验证的是**指令集执行正确性和交叉编译产物的可运行性** ——
   它证明代码在 ARM 上不会有 x86 特有的未定义行为，
   而且完整的协议栈逻辑（SIP 信令、PS 打包、RTP 时序）在用户态是**真实执行**的。
   它不验证的是：硬件外设、中断、驱动，以及硬件编码器 SDK 的调用。
   所以我通常会把 x86 原生和 aarch64 两个版本跑同一套全链做对照，
   这样能排除架构差异导致的问题。"

**追问：真机上你的代码要改哪里？**
→ "主要是码流来源。开发时是从 FIFO 读，
   真机上是调 SoC 的 VENC 出流接口，比如海思的 `HI_MPI_VENC_GetStream`
   和 `HI_MPI_VENC_ReleaseStream` —— 取用还要配对释放，否则编码器缓冲会耗尽。
   好在这部分被封装在媒体源接口后面，PS 封装和 RTP 发送那两层完全不用改，
   因为硬件编码器对应用层就是个'出码流的东西'。"

**追问：为什么用 `-O2`？**
→ "嵌入式资源紧张，不带优化跑不动。
   不过调试阶段我会先编一个 `-O0 -g` 的版本，方便用 gdb 定位。"
