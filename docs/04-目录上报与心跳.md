# 04 目录上报与心跳

> **一句话**：注册只是"我到了"。要让平台能点播，设备还得告诉它
> "我底下有哪些通道"（Catalog），并定期说"我还活着"（Keepalive）。
> 这两件事都用 SIP 的 `MESSAGE` 方法，body 里装一段 XML。

---

## ① 这一步解决什么问题

注册完成后，平台知道"有个设备在线"，但还不知道：

- 这台设备**有哪些通道**？NVR 可能挂 16 路，IPC 通常只有 1 路。
- 设备**还在不在线**？（UDP 是无连接的，平台没法感知掉线）

国标用三个 XML 消息解决：

| 消息 | 方向 | 作用 |
|---|---|---|
| **Keepalive** | 设备 → 平台 | 心跳，默认 60 秒一次 |
| **Catalog** | 平台问 → 设备答 | 目录：我有几个通道，各叫什么 |
| **DeviceInfo** | 平台问 → 设备答 | 设备信息：厂商、型号、固件版本 |

---

## ② 协议长什么样

### 先解释缩写

| 缩写 | 全称 | 人话 |
|---|---|---|
| **MANSCDP** | MAN SC DP | 公共安全行业标准里的设备控制描述协议，就是"国标定义的这套 XML" |
| **SN** | Sequence Number | 会话序号。设备应答时**必须回填请求里的 SN** |
| **Catalog** | 目录 | 通道列表 |
| **PTZ** | Pan-Tilt-Zoom | 云台：左右转、上下转、变焦 |
| **CivilCode** | 行政区划码 | 设备所在地的行政区划代码，如 `440300` = 深圳市 |

### Keepalive 心跳

```xml
<?xml version="1.0" encoding="UTF-8"?>
<Notify>
<CmdType>Keepalive</CmdType>
<SN>1</SN>
<DeviceID>34020000001320000001</DeviceID>
<Status>OK</Status>
</Notify>
```

装在 SIP MESSAGE 里发出：

```text
MESSAGE sip:44030000002000000001@4403000000 SIP/2.0
Via: SIP/2.0/UDP 127.0.0.1:5061;rport;branch=z9hG4bK...
From: <sip:34020000001320000001@4403000000>;tag=...
To: <sip:44030000002000000001@4403000000>
Call-ID: ...
CSeq: 5 MESSAGE
Content-Type: Application/MANSCDP+xml
Content-Length: 152

<?xml version="1.0" encoding="UTF-8"?>
<Notify>...</Notify>
```

**三个必须记住的点**：

1. `Content-Type` 是 `Application/MANSCDP+xml`，不是 `text/xml`。
   平台按这个类型决定用哪个解析器。
2. `Content-Length` 必须等于 body 的**字节数**（不是字符数）。
   中文名在 UTF-8 下 1 个汉字 3 字节，算错会导致 body 被截断。
3. 这是**设备主动发**的，不需要平台先问。

### Catalog 目录应答

平台发问：

```xml
<Query>
<CmdType>Catalog</CmdType>
<SN>17430</SN>
<DeviceID>34020000001320000001</DeviceID>
</Query>
```

设备应答：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<Response>
<CmdType>Catalog</CmdType>
<SN>17430</SN>
<DeviceID>34020000001320000001</DeviceID>
<SumNum>1</SumNum>
<DeviceList>
<Item>
<DeviceID>34020000001320000001</DeviceID>
<Name>TS模拟摄像头</Name>
<Manufacturer>TS</Manufacturer>
<Model>SIM-IPC</Model>
<CivilCode>440300</CivilCode>
<Parental>0</Parental>
<RegisterWay>1</RegisterWay>
<Status>ON</Status>
<PTZType>0</PTZType>
</Item>
</DeviceList>
</Response>
```

**SN 必须回填 `17430`。** 平台靠它匹配"我发的哪个查询，收到了哪个应答"。
回填错了，现象是"网页上设备信息区一直转圈"，而且没有任何错误提示。

`SumNum` 是通道总数。多通道设备的 `DeviceList` 里会有多个 `<Item>`。

**`Status` 在 `Catalog` 应答里是 `ON`；在 `DeviceInfo` 应答里是 `Result` = `OK`。**
两个结构不一样，别混。

## ③ 代码怎么长出来的

`gb_manscdp.c` 只有四个函数，全是 `snprintf` 拼字符串：

```c
int gb_xml_keepalive(char *buf, size_t cap, long sn);
int gb_xml_catalog_response(char *buf, size_t cap, long sn);
int gb_xml_device_info(char *buf, size_t cap, long sn);
void gb_xml_parse_query(const char *body, long *sn, char *cmd, size_t cmd_cap);
```

### 编码坑（原项目真实踩过）

原代码的 XML 声明写的是：

```c
"<?xml version=\"1.0\" encoding=\"GB2312\"?>\n"
```

但设备名 `TS模拟摄像头` 在 C 源码里是 **UTF-8 字节**（源文件就是 UTF-8）。
**声明说是 GB2312，实际发的是 UTF-8。** 平台按 GB2312 去解 UTF-8 字节，中文必然乱码。

本项目的处理：统一声明 `UTF-8`（GB/T 28181-2016 允许），源码与字节一致。

```c
#define GB_MANSCDP_XML_DECL "<?xml version=\"1.0\" encoding=\"UTF-8\"?>\n"
```

**这条经验可以推广到所有协议实现**：
> XML/JSON 的编码声明必须和实际字节一致。
> 不一致时**不会报错**，只会乱码 —— 而乱码往往出现在别人的界面上，
> 你这边看不到，所以特别难发现。

### 解析：不要写复杂 parser

国标应答里的 XML 结构极简单且固定，用 `strstr` 找标签就够了：

```c
const char *snp  = strstr(body, "<SN>");
const char *cmdp = strstr(body, "<CmdType>");
if (snp)  sscanf(snp + 4,  "%31[^<]", sn_s);   /* 读到下一个 '<' 为止 */
if (cmdp) sscanf(cmdp + 9, "%63[^<]", cmd);
```

**为什么不用 XML 库？** 嵌入式环境里，为了读两个字段引一个 libxml2（几 MB）不值得。
但要说清代价：这个做法**不处理命名空间、不处理转义、不处理 CDATA**。
国标消息结构固定，所以够用；如果换成通用 XML，就必须上正经 parser。

面试时这个取舍要主动说 —— **"我知道它不够健壮，我知道为什么在这里够用"**，
比"我写了个通用解析器"更能体现判断力。

## ④ 怎么验证

```bash
./build/gb28181_device -c config.ini
```

期望日志：

```
[SIP] 注册成功（200 OK）
[SIP] 心跳 Keepalive 已发送          ← 每 60 秒一次
[SIP] 收到 MESSAGE 查询: Catalog
[SIP] 已上报目录（通道 34020000001320000001）
```

平台侧验证：**打开 wvp 网页 → 设备列表应该能看到设备且状态"在线"，
点进通道列表应该能看到一个通道。** 这两处能看到，说明心跳和目录都对了。

抓包验证（可选）：

```bash
sudo tcpdump -i any -A -s0 udp port 5060 and 'udp[8:4] = 0x4d455353' 
# 只看 MESSAGE 方法开头的包；-A 打印 ASCII，能直接看到 XML
```

## ⑤ 常见坑

| 坑 | 现象 | 定位 |
|---|---|---|
| SN 没回填请求里的值 | 网页设备信息区一直转圈 | 抓包对比请求和应答的 SN |
| XML 声明编码与实际不符 | 中文名乱码，但结构正常 | 声明统一 UTF-8 |
| `Content-Length` 按字符数算 | 平台只解析到一半 XML | 用 `strlen`（UTF-8 下即字节数） |
| `Content-Type` 写错 | 平台不解析 body | 必须是 `Application/MANSCDP+xml` |
| 心跳周期太长 | 平台判定设备离线 | 通常 60 秒；平台侧一般 3 个周期无心跳就踢 |
| Catalog 里 `SumNum` 与 `Item` 数不符 | 平台显示通道数不对 | 两者必须一致 |

## ⑥ 面试怎么答

**问：设备怎么让平台知道自己在线、有哪些通道？**

> "注册完成后，设备每 60 秒发一次 Keepalive 心跳，装在 SIP 的 MESSAGE 方法里，
> body 是 MANSCDP 定义的 XML，Content-Type 是 Application/MANSCDP+xml。
> 通道信息是平台发 Catalog 查询、设备回 Catalog 应答，
> 应答里列出每个通道的 DeviceID、名称、状态。
> 关键是应答里必须回填请求的 SN，否则平台匹配不上。"

**追问：心跳断了会怎样？**
→ "平台通常连续几个周期收不到心跳就判定设备离线，从设备列表里置为离线态。
   设备侧则要注意 Expires 到期前重新 REGISTER。"

**追问：XML 解析用的什么库？**
→ "没用库，国标这几个消息结构固定，我用 `strstr` 找标签、`sscanf` 取值就够了。
   我知道这不处理命名空间和转义 —— 如果换成通用 XML 就必须上正经 parser。
   嵌入式环境里为两个字段引几 MB 的库不划算，这是个明确的取舍。"
