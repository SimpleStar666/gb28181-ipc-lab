# 02 环境搭建：把平台跑起来

> **一句话**：跑通 GB28181 需要两个平台组件（SIP 信令 + 流媒体），
> 外加一个数据库。这一章讲清它们各自干什么、为什么不能省。

---

## ① 这一步解决什么问题

前 8 个 kata 和单元测试都不需要平台 —— 它们只看字节。
但要验证"一台设备真的能被平台点播出画面"，就必须有一个平台。

这一章的目标：在 WSL2 里搭出一个最小可用的 GB28181 平台，
让你能亲手跑一遍 `REGISTER → INVITE → RTP → RTSP 出画面`。

---

## ② 平台长什么样

```
┌──────────────────────── WSL2 Ubuntu-20.04 ────────────────────────┐
│                                                                    │
│  ┌──────────────┐   SIP/UDP 5060    ┌──────────────────────────┐   │
│  │  wvp-pro     │◄─────────────────►│  设备模拟器（本项目）      │   │
│  │  SIP 信令平台 │                   │  ./build/gb28181_device  │   │
│  │  (Java)      │                   └──────────┬───────────────┘   │
│  │  :18080 web  │                              │ RTP/UDP 推流      │
│  └──────┬───────┘                              │ 目标端口由 INVITE  │
│         │ 读写设备信息                          │ 的 SDP 指定       │
│         ▼                                      ▼                   │
│  ┌──────────────┐                    ┌──────────────────────────┐  │
│  │  MySQL :3306 │                    │  ZLMediaKit              │  │
│  │  (wvp 的库)  │                    │  :11000 收流 (GB28181)    │  │
│  └──────────────┘                    │  :554   RTSP 分发         │  │
│  ┌──────────────┐                    │  :8090  HTTP API          │  │
│  │  Redis :6379 │                    └──────────┬───────────────┘  │
│  │  (会话缓存)   │                               │                  │
│  └──────────────┘                               ▼                  │
│                                          ffplay / VLC 拉流         │
└────────────────────────────────────────────────────────────────────┘
```

### 为什么不能只装一个？

| 组件 | 职责 | 少了它会怎样 |
|---|---|---|
| **wvp-pro** | SIP 信令：收 REGISTER、发 INVITE、管设备列表、给网页提供接口 | 没人给设备发 INVITE，设备永远不推流 |
| **ZLMediaKit** | 媒体：收 RTP、解 PS、建流、转成 RTSP/HLS/FLV 分发 | 信令通了但没人收包，点播会"收流超时" |
| **MySQL** | wvp 的持久化：设备表、通道表、用户表 | wvp 起不来（配置里写死要连库） |
| **Redis** | wvp 的会话与缓存 | wvp 能起来但登录/点播异常 |

**这是国标部署的典型形态：信令面与媒体面分离。**
面试时如果被问"你们平台怎么部署的"，说清这个分离就是加分项。

## ③ 组件版本与端口规划

WSL 开了**镜像网络模式**（`networkingMode=mirrored`）后，WSL 与 Windows 共享网络栈，
Windows 上已占用的端口会直接影响 WSL。实测踩到的冲突：

| 服务 | 默认端口 | 被谁占了 | 改成 |
|---|---|---|---|
| RTMP | 1935 | mediamtx（之前实验装的） | 19350 |
| HTTP | 80 | 系统服务 | 8090 |
| HTTPS | 443 | 系统服务 | 4430 |
| WebRTC | 8000 | 系统服务 | 18000 |
| **GB28181 收流** | **10000** | **Windows 侧百度网盘 `YunDetectService.exe`** | **11000** |

最终端口表：

```
wvp-pro      : 18080 (web)  /  5060 (SIP, TCP+UDP)
ZLMediaKit   : 8090 (HTTP API) / 11000 (GB28181 收流, UDP+TCP)
               / 554 (RTSP) / 19350 (RTMP)
MySQL        : 3306
Redis        : 6379
```

**这条排查经验本身值得记住**：镜像网络下，`ss -tlnp` 看不到 Windows 进程，
但端口确实被占。排查方式是"在 Windows 侧用 `netstat -ano` 找 PID，
再 `tasklist` 对名字"。原项目在这里卡了很久 —— 因为现象是"ZLMediaKit 启动了但收不到流"，
完全看不出是端口冲突。

## ④ 安装要点

### ZLMediaKit

```bash
git clone --recurse-submodules https://github.com/ZLMediaKit/ZLMediaKit.git
cd ZLMediaKit && mkdir build && cd build
cmake .. -DCMAKE_BUILD_TYPE=Release
make -j4            # 不要 -j32
```

**`make -j32` 会 OOM。** WSL 默认只分到宿主一半内存（16G 机器 → 7.8G），
32 个并行编译进程瞬间吃满。这是环境问题不是代码问题，但很浪费时间。
先用 `free -h` 看一眼可用内存再决定 `-j` 的值。

编译产物里有 `test_ps` / `test_rtp` 等教学工具，值得留着对照。

### wvp-pro

```bash
mkdir -p ~/wvp && cd ~/wvp
# 下载 release jar（v2.7.4 系列）
```

关键配置（`application.yml`）：

```yaml
sip:
  ip: 192.168.0.197        # WSL 的实际 IP，不是 127.0.0.1
  port: 5060
  domain: 4403000000       # 深圳的行政区划代码
  id: 44030000002000000001 # 平台国标编码
  password: 12345678

media:
  id: zlmediakit-local     # ★ 必须与 ZLMediaKit config.ini 里的 mediaServer id 一致
  ip: 127.0.0.1
  http-port: 8090
  secret: <ZLMediaKit 的 api secret>
  rtp:
    port-range: 40000,45000
```

### 数据库：用 MySQL，不要用 h2

原项目在这里走了弯路，三条教训：

**坑一：Spring 的 `sql.init` 在 `h2:mem` 上静默不执行。**
数据库一直是空的，但没有任何报错。现象是"wvp 启动了，但登录说用户不存在"。

**坑二：官方 h2 schema 缺表。**
2.7.4-h2 的 schema 里没有 `wvp_jt_terminal` / `wvp_jt_channel`（JT1078 模块的表），
缺表在运行时报错才发现。

**坑三（最隐蔽）：jar 与 SQL 版本错配。**
master 分支构建的 jar 会查询 `wvp_device.register_time` / `keepalive_time`，
但配套的初始化 SQL 建表语句里没有这两列（官方更新脚本反而把它们 DROP 了）。
现象是启动就报 `Unknown column`。

```sql
-- 解法：手动补列
ALTER TABLE wvp_device ADD COLUMN register_time DATETIME NULL;
ALTER TABLE wvp_device ADD COLUMN keepalive_time DATETIME NULL;
```

**这条经验的通用价值**：接手别人打包的二进制 + 别人写好的建表脚本时，
"版本对不上"是常态。判断方法永远是看日志里的具体 SQL 错误，而不是猜。

## ⑤ 怎么验证平台真的起来了

不要看进程在不在，要看**四个可观测点**：

```bash
# 1. wvp web 可达（Windows 侧直连，验证镜像网络互通）
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:18080/
# 期望 200

# 2. SIP 端口在听（TCP + UDP 都要）
ss -tlnp | grep 5060
ss -ulnp | grep 5060

# 3. wvp 日志里的四行关键信息
journalctl -u wvp | grep -E 'SIP SERVER|ZLM-连接成功|媒体节点|媒体服务节点'
#   [SIP SERVER] udp://192.168.0.197:5060 启动成功
#   [ZLM-连接成功] ID：zlmediakit-local
#   [媒体节点] 上线
#   [媒体服务节点] 设置成功

# 4. 数据库表结构已就位
mysql -u root -p wvp -e "DESCRIBE wvp_device;" | grep -E 'register_time|keepalive_time'
```

**四条全过才叫"平台就绪"。** 只过前两条的话，设备能注册但点播会失败。

### 服务化：不要用 nohup

原项目踩过：`nohup ./MediaServer &` 在 `wsl.exe -e` 的会话退出时被清理掉。
正确做法是写成 systemd 服务（`zlm.service` / `wvp.service`），
这样进程退出会被自动拉起，也不依赖交互会话。

## ⑥ 常见坑速查

| 现象 | 先查什么 |
|---|---|
| wvp 启动失败，报 `Unknown column` | jar 与 SQL 版本错配 → 看日志里的列名，手动 ALTER |
| wvp 起了但登录说用户不存在 | 数据库是空的 → 检查是不是用了 h2:mem |
| 设备注册成功，点播"收流超时" | ZLMediaKit 的收流端口（这里是 11000）通不通；或 PS 结构有问题（见 [11 章](11-排障手册.md)） |
| ZLMediaKit 日志说找不到 mediaServer | wvp yml 的 `media.id` 与 ZLM `config.ini` 的 id 不一致 |
| `ss` 看不到占用但端口起不来 | 镜像网络下 Windows 进程也占端口 → 回 Windows 侧 `netstat -ano` |
| WSL 整个卡死无响应 | 内存被 java+mysql+redis+zlm 吃光 → `wsl --shutdown` 后服务化重启 |

## ⑦ 面试怎么答

**问：你们这套 GB28181 平台是怎么部署的？**

> "信令面和媒体面分离。信令用 wvp-pro（Spring Boot），负责 SIP 注册、设备管理、
> 目录订阅和点播控制，数据落 MySQL；媒体用 ZLMediaKit，负责 GB28181 收流、
> PS 解封装、建流和 RTSP/FLV 分发。设备端只跟 SIP 服务器做信令交互，
> 推流目标地址由 INVITE 的 SDP 指定。"

**追问：遇到过什么部署问题？**
→ 讲端口冲突那条（镜像网络 + Windows 进程占 10000 端口，
   现象是"服务起来了但收不到流"，排查要回 Windows 侧看 `netstat -ano`）
   → 讲 jar/SQL 版本错配（`register_time` 列缺失，靠日志里的列名定位）

**追问：为什么用 MySQL 不用内置数据库？**
→ 讲 h2:mem 上 `sql.init` 静默不执行这条 —— 这种"没报错但是空的"最难查，
   所以宁愿上真数据库。
