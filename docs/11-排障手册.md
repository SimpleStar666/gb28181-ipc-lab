# 11 排障手册：20 条真实踩坑链

> **这一章是这个项目最值钱的部分。**
>
> 代码谁都能抄，但"从现象推到根因"的能力抄不走。
> 下面每一条都是真实发生过的：有现象、有根因、有定位手段、有修法。
>
> **面试时的用法**：不要主动全讲。等对方问"遇到过什么困难"，
> 挑 2–3 条最贴合岗位的（PS 结构类 + 时序类）讲透，
> 要讲到"我怎么定位"而不只是"我改了什么"。

## 排障总原则

### 三层定位法

遇到"没有画面"，**永远按这个顺序缩小范围**，不要瞎猜：

```
第 1 层：设备侧日志
         注册成功了吗？   → 没成功：鉴权/网络问题（看 A 组）
         收到 INVITE 了吗？→ 没收到：信令问题
         推流线程起了吗？  → 没起：SDP 解析问题
         推了多少帧？      → 帧数不涨：媒体源问题

第 2 层：平台侧
         ZLM 收到包了吗？  → 没收到：RTP 目标地址/端口问题
         建流了吗？        → 没建流：PS 结构问题（看 B 组）

第 3 层：字节
         把收到的 PS dump 出来，逐字节核对结构
```

### 三个"证据优于推测"的手段

| 手段 | 用途 |
|---|---|
| **`ZLM dumpDir`** | 让 ZLMediaKit 把收到的原始流 dump 到磁盘。`.video` 是解析产物，**0 字节 = 根本没解析出 track**。这是"平台到底收到了什么"的唯一硬证据 |
| **`ffprobe <dump>`** | 拿 dump 出来的文件喂给 ffmpeg。能解 = 流本身没问题（是 ZLM 配置问题）；不能解 = 流真的坏了 |
| **按起始码扫描的脚本** | 逐字节核对第一帧结构。**排除推测，只信字节** |

### 判定口径：看证据，不看返回码

平台 API 有时会返回 `-2 收流超时`，但同时：
- 抓帧两次，**两个 md5 不同**（画面在动）
- 画面内容正确（不是花屏）

**这时链路实质是通的。** 返回码可能是平台的超时判定与设备推流启动时序没对齐。

> **这条经验很重要**：不要被单一信号（返回码）绑死。
> 交叉验证多个独立证据，再下结论。

## A 组：注册与鉴权

### A1. `mediaServerId` 配置不一致 → 推流鉴权失败

**现象**
设备注册成功，点播也有响应，但 ZLMediaKit 日志说
"找不到对应的 mediaServer"，推流被拒。

**根因**
wvp-pro 的 `application.yml` 里 `media.id` 必须与
ZLMediaKit `config.ini` 里 hook 配置的 id 完全一致。
任一侧写的是模板默认值（比如 `your_server_id`），就匹配不上。

**定位**
```bash
grep -A3 '^media:' ~/wvp/application.yml
grep -B2 -A8 'hook' ~/ZLMediaKit/release/linux/Release/config.ini | grep -i id
```

**修法**
两边改成同一个值（如 `zlmediakit-local`）。
**注意**：改配置时用 `sed` 要小心，容易误伤同名的 `sip` 段的 `id` 字段 ——
改完一定 `grep` 复查一遍。

**面试价值**：说明你理解"信令平台和媒体平台是两个组件，靠 id 关联"。

---

### A2. MD5 常量写错 → 注册回 403

**现象**
平台回 `403 Forbidden`，提示像是密码错误。
但密码反复确认是对的。

**根因**
RFC 1321 MD5 的 Round 1 第 15 步常量应为 `0xa679438e`，
代码里写成了 `0xa6434387`。

**为什么特别难查**
**四个文件都写了同一个错值**（三份"独立"实现 + 一份拷贝）。
改 A 用 B 验证，B 也是错的，互相"印证"，形成**假一致**。
而且现象是 403，让人一直往密码方向查。

**定位**
```c
/* 跑标准测试向量 —— 这是唯一的权威判据 */
md5("")    == "d41d8cd98f00b204e9800998ecf8427e"  ?
md5("abc") == "900150983cd24fb0d6963f7d28e17f72"  ?
```

**修法**
改成 `0xa679438e`，用标准向量验证通过。

**面试价值**：★★★★★
这个坑能同时展现三件事：
① 会自己实现密码学原语（不引 OpenSSL）
② 知道自实现的风险
③ **懂得"跨实现验证必须用外部标准向量，不能自己跟自己对"** ——
   这是很好的工程判断力体现。

---

### A3. 只实现了 `qop=auth` 分支 → 换平台就失败

**现象**
在自己的测试平台上注册正常，换一个平台必失败，只回一个含糊的 403。

**根因**
Digest 鉴权有两条分支：带 `qop` 和不带 `qop`。
只实现了一条。

**定位**
抓包看 401 响应里的 `WWW-Authenticate` 头有没有 `qop=` 参数。

**修法**
两条分支都实现（见 [03 章](03-SIP注册与Digest鉴权.md)）。

**面试价值**：体现"不要只按自己测过的环境写代码"。

## B 组：PS 结构（最核心的一组）

### B1. ffmpeg 的 `-f vob` 缺 PSM

**现象**
用 `ffmpeg -f vob` 生成的"PS"流，ffprobe 认不出编码。

**根因**
`vob` muxer 生成的是 DVD 用的私有 PS 变体，**不带 Program Stream Map**。
没有 PSM，接收端就不知道 `stream_id 0xE0` 里装的是什么编码。

**定位**
hexdump 找 `00 00 01 BC`（PSM 起始码）—— 找不到就是缺 PSM。

**修法**
改用 `-f mpeg`（标准 MPEG-2 PS）。

**面试价值**：引出 PSM 的必要性。

---

### B2. ffmpeg 根本无法输出 H.264-in-PS → 自研打包器

**现象**
`-f vob` 和 `-f mpeg` 都试过，**都不支持 H.264**。
ffmpeg 的 PS muxer 只支持 MPEG-2 video / MPEG-1 audio 那套老编码。

**根因**
不是配置问题，是 ffmpeg 的能力边界。

**修法**
**自己写 PS 打包器**：
```bash
ffmpeg -f h264 裸流输出 → 自己组 Pack/System/PSM/PES
```

**面试价值**：★★★★★
这是本项目"自研 PS 打包器"的由来。
面试讲这条时，重点不是"我写了个打包器"，
而是**"我先试了标准工具，发现它能做的边界在哪，然后才决定自己实现"** ——
这个决策过程比结果更能说明能力。

---

### B3. PES 头的 `flags1` 必须是 `0x80`

**现象**
ffprobe 报 `Invalid data`。

**根因**
PES 头第 7 个字节（`flags1`）的最高两位必须是 `10`（ISO 13818-1 规定）。
误写成 `0x10`（最高两位 `00`）后，解析器认为这是非法值。

**定位**
```bash
xxd frame.ps | grep -A1 '0001 e0'
#              └─ 看 PES 头第 7 字节
```

**修法**
`0x80`。

**面试价值**：说明你读过规范，不是试出来的。

---

### B4. ★ Pack Header 首字节是「PES 解析模式开关」

**现象**
PES 头字节明明对，但 ffprobe 还是报错位。

**根因**
Pack Header 第 5 个字节（`00 00 01 BA` 之后那个）：

| 值 | 最高两位 | 含义 |
|---|---|---|
| `0x21` | `00` | **MPEG-1 PS** → PES 按 MPEG-1 规则解析 |
| `0x44` | `01` | **MPEG-2 PS** → PES 按 MPEG-2 规则解析 |

MPEG-1 的 PES 头结构和 MPEG-2 **完全不同**
（MPEG-2 多了 `flags` 那 3 个字节）。
写成 `0x21` 时，你精心构造的 `80 80 05` PES 头会被按 MPEG-1 解析 → 整体错位。

**定位**
看 Pack Header 第 5 字节。

**修法**
`0x44`。

**面试价值**：★★★★★
**这是"不显眼但关键"字段的最佳案例。**
面试问"PS 里哪个字段最容易被忽略但影响最大"，这就是答案。
它体现的是"我知道接收端会怎么解析我这块字节"，而不只是"我按格式填了"。

---

### B5. PSM 少了 → 整个流建不起来

**现象**
设备在推流，网络上有包，但 ZLMediaKit **15 秒收流超时**，
`.video` dump 是 **0 字节**。

**根因**
ZLMediaKit 的 `mpeg-ps-dec.c`：

```c
static struct pes_t* psm_fetch(struct psm_t* psm, uint8_t sid)
{
    for (i = 0; i < psm->stream_count; ++i)
        if (psm->streams[i].sid == sid) return &psm->streams[i];
    return NULL;        /* ← 没声明就返回 NULL */
}
```

PES 包按 `stream_id` 去 PSM 里查，**查不到就丢弃这个 PES**。
PSM 里没声明 H.264，所有视频 PES 都被丢掉。

**定位**
```bash
# 1. 找 PSM
xxd frame.ps | grep '0001 bc'

# 2. 核对长度字段
#    packet_length 应该 = PSM 总长 - 6
```

**修法**
PSM 里必须有 `stream_type=0x1B(H.264)` / `elementary_stream_id=0xE0` 这条。
含音频时还要有 `0x90 / 0xC0`。

**面试价值**：★★★★★
这条能一路讲到 ZLMediaKit 源码，是"我真读过下游实现"的硬证据。

---

### B6. PES 头 `memcpy` 少拷 1 字节（13 写成了 14 的一半）

**现象**
C 移植后，x86 和 aarch64 **都** 出现"收流超时"。
PS 字节"看起来"和 Python 版一致。

**根因**
```c
memcpy(ps + ps_len, pes_hdr, 13);   /* ✗ PES 头实际是 14 字节 */
memcpy(ps + ps_len, pes_hdr, 14);   /* ✓ */
```
PES 头 = start_code(4) + length(2) + flags(3) + PTS(5) = **14 字节**。
少拷 1 字节 → PTS 第 5 字节（marker）丢失 → 整个 PS 错位 1 字节。

**定位**
逐字节对比 Python 版和 C 版生成的第一帧抓包。

**面试价值**：说明"看起来一样"和"字节一样"是两回事。

---

### B7. ★ PSM 数组少写 1 个 `0x00`（真正的根因）

**现象**
同 B6，但改完 PES 头还是不通。

**根因**
```c
/* Python 版：20 字节 */
00 00 01 BC 00 0E 01 01 00 00 00 04 1B E0 00 00 00 00 00 00

/* C 版：数组只写了 19 字节，漏了最后 1 个 0x00 */
00 00 01 BC 00 0E 01 01 00 00 00 04 1B E0 00 00 00 00 00
```

`program_stream_map_length = 0x0E` 声称后面有 14 字节，
但实际只有 13 字节 → 解析 PSM 时长度错位 → 后面的 PES 全部错位 → 不建流。

**定位**
**数一遍。** 这是唯一的方法。
`packet_length = 总长 - 6` → 20 - 6 = 14 = `0x0E` ✓

**修法**
补齐第 20 个字节。

**面试价值**：★★★★★
**"少一个字节，全部功能失效，而且现场看不出任何异常"** ——
这是讲协议实现严谨性最好的故事。
配合 B5 一起讲：一个讲"结构要对"，一个讲"长度要对"。

## C 组：分帧与码流

### C1. libx264 多 slice 被当成多帧

**现象**
ffmpeg 报 `DTS out of order`，ZLM 不建流。

**根因**
libx264 多线程默认把一帧切成 3 个 slice。
分帧逻辑用"撞到 slice = 一帧结束"判定，于是 1 帧被当 3 帧，
PTS 递增了 3 次 → 时间戳乱序。

**定位**
看日志里同一时间段的 PTS 增长是否成倍。

**修法**
编码时强制单 slice：
```bash
-threads 1 -x264-params slices=1
```

**面试价值**：★★★
注意：**这是排障故事，不是面试考点。**
面试考的是"帧边界怎么判定"（撞到 VCL NAL 就是一帧），
而不是"x264 的哪个参数叫什么"。讲的时候要把重点放在判定逻辑上。

---

### C2. 流式切分丢掉跨 chunk 的 NAL

**现象**
每帧都有轻微花屏（解码器 concealing）。

**根因**
旧实现"找到 start code 后丢弃整块已处理数据"，
如果一个 NAL 被 `read()` 边界切成两半，后半部分就被丢了。

**定位**
看解码器日志里的 concealment 计数。

**修法**
保留未消费尾部（见 [08 章](08-实时流与音频轨.md)）：
```c
if (f2 < 0) { pos = (size_t)f1; break; }   /* 不完整，等更多数据 */
```
外层 `memmove` 把尾部搬到缓冲区头部。

**面试价值**：★★★★
体现"流式处理 vs 批处理"的差别。这是嵌入式媒体处理的典型问题。

---

### C3. ★ PS 载荷必须保留起始码

**现象**
切分逻辑改好之后，反而**首包正常、之后 15 秒无 track**（收流超时）。

**根因**
新的切分逻辑"规范化"地剥离了 `00 00 00 01` 起始码，
只把 NAL 内容放进 PS。

但 **ZLMediaKit 的 `GB28181Process` 依赖起始码来切 NAL** ——
没有起始码，它找不到 NAL 边界，解析不出 track。

**定位**
dump 出 PS，看 PES 载荷开头是不是 `00 00 00 01 65`。
是 → 有起始码；直接是 `65` → 被剥离了。

**修法**
切分时**保留起始码**，NAL 类型按"含起始码的偏移"读。

**面试价值**：★★★★★
**这是最反直觉的一条。** "把数据规范化"是好习惯，
但在协议实现里，**下游可能依赖那些看起来'冗余'的字节**。
讲这条能体现"我知道我的输出会被谁怎么消费"。

---

### C4. 实时流首帧不是关键帧 → 解不出来

**现象**
实时模式启动后，画面长时间不出现或花屏。

**根因**
新连接开始时，缓冲区第一个字节可能是任意位置的半个 NAL，
推出去接收端没法初始化解码器。

**修法**
锚定到 SPS（NAL 类型 7）：
```c
if (!got_anchor) {
    if (nal_type == 7) got_anchor = 1;
    pos = f2; continue;         /* 锚定前全部丢弃 */
}
```

**为什么锚 SPS 而不是 IDR**：一帧完整关键帧是 `[SPS][PPS][SEI][IDR]`，
锚在 SPS 才能让它们进同一个 PES。锚在 IDR 就把 SPS/PPS 丢掉了。

配套：编码时加 `repeat-headers=1`，让每个关键帧都重带 SPS/PPS。

**面试价值**：★★★★

---

### C5. 滚动缓冲 `pos < stream_used` → 画面卡住

**现象**
实时推流跑一段时间后画面卡住，但程序没崩、日志还在打。

**根因**
```c
if (pos < stream_used) { memmove(...); stream_used -= pos; }   /* ✗ */
```
当一轮数据**恰好全部消费完**时，`pos == stream_used`，
条件不成立 → 不滚动 → `stream_used` 不清零 →
下一轮新数据追加在旧数据后面 → **旧数据被重复推流** → 流错乱。

**修法**
```c
if (pos > 0) { memmove(stream_buf, stream_buf + pos, stream_used - pos); stream_used -= pos; }
```
`memmove` 长度 0 时自然就把 `stream_used` 归零了。

**面试价值**：★★★★
**"边界条件写'精确'不等于写'正确'"** —— 这个总结很有分量。

## D 组：RTP 时序

### D1. marker 位写到 bit0 → 解码崩

**现象**
ffmpeg 报 `mb_type 384` 之类的解码错误。

**根因**
```c
rtp[1] = pt | (last ? 0x01 : 0);   /* ✗ PT 从 96 变成 97 */
rtp[1] = pt | (last ? 0x80 : 0);   /* ✓ marker 在第 1 字节最高位 */
```

**定位**
抓包看 RTP 头第 2 字节：
`0x60` = M=0/PT=96 ✓，`0xE0` = M=1/PT=96 ✓，**`0x61` = M=0/PT=97 ✗**

**面试价值**：★★★★
一个字符的差别，一个 7 位字段就废了。
**"位域操作一定要抓包验证"** 是很好的经验总结。

---

### D2. RTP timestamp 与 PES PTS 不同源 → 帧序乱

**现象**
画面能出但时序错乱。

**根因**
RTP 头和 PS 里的 PTS 来自**两个不同的累加器**，
或者一个用 90kHz 一个用了别的时钟。

**修法**
**同一个值**：RTP timestamp 直接取 PES PTS（都在 90kHz 域）。

**面试价值**：★★★★

---

### D3. ffmpeg 的 `-re` 在 WSL 里失效 → 超速推流

**现象**
模拟器以 65fps 全速推流（而不是 15fps），
ZLMediaKit 收流 1.5–3 秒后断流。

**定位**
```bash
timeout 5 ffmpeg -re -i ... -f h264 - | wc -c
# 期望 45KB（15fps），实测 195KB（65fps）
```

**根因**
`-re` 在 WSL 环境下不生效。超速推流导致 ZLM 的 EPOLLET（边缘触发）
竞态 —— 数据来得比消费快，边缘触发模式下会漏掉事件。

**修法**
**不依赖 `-re`，设备侧自己限速**：
```c
usleep(FRAME_INTERVAL_MS * 1000);   /* 66ms → 15fps */
```

**面试价值**：★★★★
**"不要依赖外部工具的一个我无法验证的行为"** ——
这个决策思路很有价值。自己限速虽然土，但确定性强。

顺带一个知识点：EPOLLET 是边缘触发，只有状态变化才通知；
配合非阻塞 socket 和循环读直到 EAGAIN 才是正确用法。
生产者超速时会踩到这个坑。

## E 组：环境与工程

### E1. 端口被 Windows 进程占（镜像网络模式）

**现象**
ZLMediaKit 启动成功，但收不到流。`ss -tlnp` 看不到占用者。

**根因**
WSL 开了 `networkingMode=mirrored` 后与 Windows 共享网络栈。
**Windows 侧的百度网盘 `YunDetectService.exe` 占了 10000 端口**（GB28181 默认收流口）。

**定位**
```powershell
# 回到 Windows 侧找
netstat -ano | findstr :10000
tasklist | findstr <PID>
```

**修法**
改 ZLMediaKit 收流口到 11000，wvp 配置同步改。

**面试价值**：★★★
体现"跨环境排查"的思路：WSL 里看不到的东西，要回宿主查。

---

### E2. `make -j32` 把 WSL 打挂

**现象**
编译中途 WSL 实例无响应。

**根因**
WSL 默认只分到宿主内存的一半（16G 机器 → 7.8G）。
32 个并行编译进程瞬间吃满。

**修法**
先 `free -h` 看可用内存，用 `-j4`。
WSL 卡死后 `wsl --shutdown` 恢复。

**面试价值**：★★ 环境常识。

---

### E3. jar 与建表 SQL 版本错配

**现象**
wvp 启动报 `Unknown column 'register_time'`。

**根因**
master 分支构建的 jar 查询 `wvp_device.register_time / keepalive_time`，
但配套的初始化 SQL 里没有这两列（官方更新脚本反而把它们 DROP 了）。

**修法**
```sql
ALTER TABLE wvp_device ADD COLUMN register_time DATETIME NULL;
ALTER TABLE wvp_device ADD COLUMN keepalive_time DATETIME NULL;
```

**面试价值**：★★★
通用教训：接手别人打包的二进制 + 建表脚本时，"版本对不上"是常态。
判断方法永远是看日志里的具体 SQL 错误，不是猜。

---

### E4. h2:mem 上 `sql.init` 静默不执行

**现象**
wvp 起来了，但登录说用户不存在。数据库是空的，**且没有任何报错**。

**修法**
换 MySQL，并导入官方初始化 SQL。

**面试价值**：★★★★
**"没有报错但结果是空的"是最难查的一类 bug。**
这条的教训是：当你无法信任一个组件的初始化行为时，换掉它比调试它快。

---

### E5. WSL 实例空闲终止 → `/tmp` 数据丢失

**现象**
脚本之间传递的文件莫名不见了；wvp/ZLM 表现为"反复重启"。

**根因**
每次 `wsl.exe -e` 调用可能拉起新实例。
实例空闲被回收后 `/tmp` 清空，systemd 重新拉起全部服务。

**修法**
- 全链在**一个 bash 脚本内**跑完
- 产物**立即拷到 `/mnt/c`**
- 服务写 systemd unit，不依赖交互会话

**面试价值**：★★★

---

### E6. root/ts 用户混用 + `/tmp` sticky bit

**现象**
手动在终端操作时 `Operation not permitted` / `Permission denied`。

**根因**
`wsl.exe -e` 默认以 **root** 运行，而手动终端是 **ts**。
`/tmp` 有 sticky bit，ts 无法删除/打开 root 创建的 FIFO。

**修法**
所有 wsl 调用统一 `-u ts`；清理 root 残留；产物 `chown ts:ts`。

**面试价值**：★★★
Linux 权限常识，但踩过才知道痛。

---

### E7. `gcc ... | head` 触发 SIGPIPE，产物不更新

**现象**
改了代码、编译"成功"、运行结果没变。

**根因**
`head` 读满就退出，gcc 继续往 stderr 写就被 SIGPIPE 杀掉，编译中断，
**产物还是上一次的旧二进制**。

**修法**
不要用管道；需要看输出就重定向到文件。

**面试价值**：★★★★
这条特别有价值，因为它解释了"为什么改代码没效果"这类灵异现象。

---

### E8. `nohup ... &` 在 wsl 会话退出时被清理

**现象**
后台起的服务一会儿就没了。

**修法**
写 systemd unit（`zlm.service` / `wvp.service`），由 systemd 管理。

**面试价值**：★★

---

### E9. ★「同一条断言，两次跑结果不同」—— 先怀疑环境，不要怀疑功能

**现象**
端到端脚本里 `BYE 收到 200 OK` 这条断言：第一次跑 FAIL，第二次跑 PASS。
而且日志里同时出现 `✓ BYE 收到` 和 `✗ BYE 没收到 200 OK` 这种自相矛盾的记录，
设备日志里还有乱码（`�送 105 帧`），以及"推流线程已退出"之后又继续推帧的记录。

**根因**（三类，全都不是"功能坏了"）

1. **残留进程**：设备端 socket 设了 `SO_REUSEADDR`，
   上一轮没杀干净的进程能和新进程**同时 bind 同一个端口**。
   于是两个设备进程都在应答平台、都在往**同一份日志文件**里写。
2. **并发写同一文件**：两个进程交错 append → 日志撕裂、乱码、记录自相矛盾。
3. **脚本用固定 deadline 等回包**：而不是事件驱动，回包稍慢就判失败。

**定位思路（这是重点）**

> **同一输入两次结果不同，只可能是"环境里有你没控制住的变量"，
> 不可能是"功能有时候对有时候错"。**
>
> 一旦看到 flake，第一反应应该是查"有没有上一次没清干净的进程"，
> 而不是去读业务代码找逻辑 bug。**把不确定性归因到功能上，方向就错了。**

顺带注意第一个线索往往在日志里：**乱码和自相矛盾的记录 = 并发写的指纹。**
单进程顺序写日志是不会产生乱码的。

**修法**

| 措施 | 解决什么 |
|---|---|
| 用 `flock` 把脚本串行化 | 两个脚本实例互抢端口、互杀进程 |
| 清场用 **pidfile + 进程名(`/proc/<pid>/comm`) + cmdline** 三重匹配 | 精确杀掉上一轮的残留，且不误伤 |
| 启动后校验"设备进程 == 1、平台进程 == 1" | 不满足就直接 FAIL，不让 flake 混进结果 |
| 各进程日志写到**各自独立的文件**，并带 PID + 时间戳头 | 杜绝撕裂；还能检测到"同一文件出现两个启动头" |
| 等回包改成**事件驱动**（收到就退出，最多重传 N 次） | 不再依赖固定超时 |

**面试价值**：★★★★★
这条比任何协议细节都更能体现工程成熟度。
它展示的是"**能把 flake 定性到根因、并用负向回归证明修好了**"的能力 ——
大多数人遇到 flake 只会重跑一次然后说"这次过了"。

### E10. `pkill -f` 把调用它的那个 shell 自己杀了

**现象**
清场脚本跑完，主脚本**无声退出**（rc=1），什么也没做。

**根因**
```bash
pkill -f -- "-c build/demo/demo.ini"      # ✗
```
`-f` 是匹配**完整命令行**。而调用这条 `pkill` 的那个 shell，
它自己的命令行里就带着 `-c build/demo/demo.ini` 这段字符串 ——
于是 `pkill` 匹配到了自己（以及自己的父 shell），把自己杀了。

**修法**
先按 cmdline 找出候选 PID，再用 `/proc/<pid>/comm` 过滤掉 shell 包装进程：
```bash
for p in $(pgrep -f -- "$PATTERN"); do
    [ "$(cat /proc/$p/comm 2>/dev/null)" = "gb28181_device" ] && kill "$p"
done
```

**面试价值**：★★★
`pkill -f` 的自匹配是个经典陷阱。凡是"脚本莫名退出且没有输出"，都值得往这个方向看一眼。

### E11. `make clean` 与验证脚本并发跑 → 一堆假红

**现象**
单元测试突然报"7 个用例编译期失败"，kata 报"5 个编译失败"。
但单独跑都好好的。

**根因**
`make clean` 是 `rm -rf build/`，而验证脚本的编译产物**也在 `build/` 下**。
两边并发跑，一边删一边编。

**修法**
- 验收流程**串行**跑：`make clean && make && make aarch64 && make test && tools/*.sh`
- 验证脚本增强抗性：检测产物缺失就自动重建一次；
  编译日志改到 `mktemp` 目录，每轮重建输出目录，不共用状态。

**面试价值**：★★★
"共享可变状态"在构建脚本里同样是万恶之源。
把中间产物放进独立目录、让脚本不依赖上一次的残留，是让 CI 稳定的基本功。
