# 00 学习地图

> **这份文档解决一个问题：13 章讲义该怎么用，才不会又变成"看一遍就忘"。**

---

## 一、先接受一个事实

GB28181 的设备端**不难，但很碎**。它不难是因为核心只有一个循环：

```
从编码器拿一帧 → 套一层 PS → 切几个 RTP 包 → UDP 发出去
```

它碎是因为这一行字里藏了四套协议规范、三个 33 位时间戳的位域、一堆长度字段，
还有"长度字段到底算不算它自己"这种必须逐字节数一遍才能确认的细节。

原项目的 795 行代码其实就是把这个循环写对了。问题在于：
**你看到的是一整块，看不出这一行对应哪条规范。**

所以本课程的做法是：**先把它拆开，一次只讲一个机制。**

## 二、三层心智模型

先建立这张图，后面每一章都往里填东西。

```
┌─────────────────────────────────────────────────────────────┐
│  第一层：信令（SIP，走 UDP 5060/5061）                        │
│    REGISTER  注册，带 Digest 鉴权                            │
│    MESSAGE   收发 MANSCDP XML（心跳 / 目录 / 设备信息）        │
│    INVITE    平台点播 → 设备回 200 OK + SDP → 拿到推流地址     │
│    BYE       停止点播                                        │
├─────────────────────────────────────────────────────────────┤
│  第二层：容器（MPEG-PS，把音视频装进同一条流）                 │
│    Pack Header → System Header → PSM → PES(H.264) → PES(G.711A)│
│    关键作用：让视频和音频共享同一个 90kHz 时钟（音画同步的根）  │
├─────────────────────────────────────────────────────────────┤
│  第三层：传输（RTP over UDP，单端口）                          │
│    12 字节头 + PS 载荷；一帧 PS 可能切成多个 RTP 包           │
│    序号管重组、时间戳管播放、marker 管"这帧完了"               │
└─────────────────────────────────────────────────────────────┘
```

记住每一层**解决什么问题**，比记住字段值重要得多：

| 层 | 解决什么问题 | 如果没有它 |
|---|---|---|
| SIP | 设备怎么被平台发现、怎么被叫起来 | 平台不知道你存在 |
| PS | 音视频怎么装一起、怎么同步 | 你得开两路 RTP，还得自己做 NTP 对齐（这就是 WebRTC 的做法） |
| RTP | 一大块数据怎么过 MTU 限制、怎么重组 | 一帧 200KB 发不出去 |

**面试时先讲这三层，再讲细节。** 考官听到你先分层，就知道你看过全局。

## 四、每一步的固定套路

每一章都是同一个结构，照着走：

```
① 这一步在解决什么问题        ← 先看这个，不要跳到代码
② 协议长什么样（配结构图）      ← 对应规范哪一节
③ 代码怎么长出来的（关键片段）  ← 不是贴全文，是讲"为什么这么写"
④ 跑哪个 kata 能看见字节        ← steps/ 下的小程序
⑤ 怎么验证"我做对了"            ← 命令 + 期望输出
⑥ 常见坑                       ← 别人踩过的
⑦ 面试怎么答                   ← 一句话版本
```

**如果只有 20 分钟，只看 ① 和 ⑦。**

## 五、8 个 kata：为什么单独拆出来

`steps/` 下 8 个独立小程序，每个 ≤180 行，不依赖主程序，单独编译就能跑：

| kata | 一次讲清 |
|---|---|
| `01_annexb_split.c` | AnnexB 起始码 + 流式切帧为什么要留残留 |
| `02_pts_encode.c` | 33 位 PTS 铺进 5 个字节的位域（**含原项目的错位 bug**） |
| `03_ps_pack.c` | 手工组一个完整 PS，逐字段标注 |
| `04_psm_layout.c` | PSM 的长度字段到底算哪些字节 |
| `05_rtp_slice.c` | 分片 + marker 位 |
| `06_md5_digest.c` | MD5 标准向量 + SIP Digest 每个缩写的含义 |
| `07_g711a.c` | A-law 编解码（中国用 A 不用 μ） |
| `08_rtp_loopback.c` | 本机 UDP 环回，把"发出去"变成"看得见" |

**为什么不做成一个大程序的分步快照？**
因为初学者需要的是"隔离变量"：一次只有一个机制在动，出错时你立刻知道是哪一层。
把 8 个机制混在 1500 行里，任何一个环节错了你都只能瞎猜。

```bash
bash tools/build_steps.sh     # 全部编译运行，汇总 PASS/FAIL
```

## 六、验证驱动：这个仓库和"抄一份代码"的区别

原项目有一个真实的 bug：MPEG-PS 的 PTS 第 3 个字节右移了一位（`>>15` 应为 `>>14`）。

**它为什么能潜伏几个月？** 因为下游 ZLMediaKit 多数路径不依赖 PES PTS，
用 RTP 时间戳也能出画面 —— **"画面正常"不等于"协议正确"**。

本仓库的应对：

| 手段 | 抓什么 |
|---|---|
| `tests/test_pts.c` | 位域：给定 PTS 断言 5 个字节，并做 33 位往返解码校验 |
| `tools/verify_pts.sh` | 打一个 `.ps` 文件，用 `ffprobe` 反读 PTS，与写入值比对 |
| **`tools/verify_pts_mutation.sh`** | **负向对照：故意把 `>>14` 改回 `>>15`，看上面两招是不是真的抓得住** |
| `tests/test_psm.c` | 长度字段：断言 `packet_length == 总长 − 6` 对两种 PSM 都成立 |
| `tests/test_rtp.c` | 断言 marker 只在最后一片、同帧所有分片 timestamp 相同 |
| `tools/demo.sh` | 端到端 18 项断言（含 Digest 闭环、SDP→RTP、SSRC、音频时间戳） |

**"我能证明它是对的" 和 "它看起来能跑"，在面试里是两回事。**

而那第三条 —— **负向对照** —— 是这里面最值钱的。
因为"我的测试全绿"永远可能是"我的测试太弱"。
只有当你**故意把 bug 放回去、然后看测试红掉**，你才真的证明了测试有效：

```
单测抓住：  gb_ps_encode_pts(90000) = [21 00 03 BF 21], expected [21 00 05 BF 21]
ffprobe 抓住：写入 PTS=90000 → ffprobe 读回 pts=57232（差 -32768 ticks / -0.3641 秒）
```

**这是"测试驱动"和"跑个测试意思一下"的分界线。**
