# 08 实时流与音频轨

> **一句话**：前面几章推的是磁盘上预生成的码流文件。
> 这一章做两件真实设备必须做的事：
> **从编码器实时读流（而不是读文件）**，以及**把音频加进来**。

---

## ① 这一步解决什么问题

到目前为止的链路是"预生成一个 `testsrc.h264`，读进来循环推"。
这能验证 PS/RTP 封装对不对，但不是真实设备的形态。

真实设备有两个必须补上的部分：

**问题一：码流是流式产生的，不是完整文件。**
编码器一帧一帧往外吐，你在缓冲区里看到的永远是"半截数据"。
一段读取的结尾很可能把某个 NAL 单元切成两半。

**问题二：没有音频。**
国标 IPC 必须有音频，而且这是 JD 里"音画同步"那条的直接落点。

---

## ② 实时流：滚动缓冲怎么设计

### 数据长什么样

编码器（或 ffmpeg 往 FIFO 里写）产生的是**连续字节流**：

```
...00 00 00 01 65 <IDR 数据> ... 00 00 01 41 <P 帧数据> ... 00 00 00 01 67 ...
                    ▲                                        ▲
                  切在这里                                  切在这里
```

你每次 `read()` 拿到的是一小块，边界是**任意的**。比如：

```
read #1: [00 00 00 01 65 88 84 ... 41 9A]      ← 结尾把下一个 NAL 切了一半
read #2: [2B 3C ... 00 00 01 41 ...]           ← 这一半才是上一个 NAL 的尾巴
```

**如果每次读完就丢弃已处理的整块，跨边界的那半个 NAL 就永久丢失了。**

后果：帧被截断 → 解码器报错 → 画面出现马赛克/花屏（concealing）。

### 解法：滚动缓冲

```c
while (streaming) {
    size_t n = fread(stream_buf + stream_used, 1, 65536, fp);
    if (n == 0) { /* 写端暂歇，重开 FIFO 等 */ continue; }
    stream_used += n;

    size_t pos = 0;
    while (1) {
        int f1 = find_sc(stream_buf, stream_used, pos, &sc_len);
        if (f1 < 0) { pos = 0; break; }                   /* 没有起始码，等更多数据 */
        int f2 = find_sc(stream_buf, stream_used, f1 + sc_len, &f2_sc);
        if (f2 < 0) { pos = (size_t)f1; break; }          /* ★ 当前 NAL 不完整，等更多 */
        /* ... 处理 [f1, f2) 这个完整 NAL ... */
        pos = (size_t)f2;
    }

    /* ★★ 把未消费的尾巴搬到缓冲区头部 */
    if (pos > 0) {
        memmove(stream_buf, stream_buf + pos, stream_used - pos);
        stream_used -= pos;
    }
}
```

`f2 < 0` 时把 `pos = f1` —— **不丢弃这个不完整的 NAL，标记为"下次从这儿继续"**。
外层循环下一轮读到新数据后，`find_sc` 就能找到它的结尾了。

### ★ 那个 `if (pos > 0)` 的 bug

原项目这里写的是 `if (pos < stream_used)`。看起来更"精确"，实际上是错的。

**出问题的场景**：某一轮读完，缓冲区里的数据**恰好被完整消费**，
此时 `pos == stream_used`。

- 条件 `pos < stream_used` → **不成立** → 不滚动 → `stream_used` 保持原值
- 下一轮 `fread` 把新数据**追加在旧数据后面**
- 于是旧数据被**重复处理** → 重复推流 → 流时序错乱 → 画面卡住

**正确条件 `pos > 0` 的含义**：只要消费了任何字节就滚动，
`memmove` 长度为 0 时自然就把 `stream_used` 归零了。

> 这个 bug 的教训很有价值：**边界条件写"精确"不等于写"正确"。**
> `pos < stream_used` 在语义上像是在说"还有剩余才需要搬"，
> 但漏掉了"全部消费完也需要把长度清零"这一步。

### 锚定 SPS：保证首帧是关键帧

新连接开始时，缓冲区里的第一个字节可能是任何东西（半个 NAL 的尾巴）。
直接推出去，接收端根本没法初始化解码器。

```c
if (!got_anchor) {
    if (nal_type == 7) {          /* 7 = SPS */
        got_anchor = 1;           /* 从这里开始收 */
    }
    pos = f2;                     /* 锚定前全部丢弃 */
    continue;
}
```

**为什么要锚在 SPS 而不是 IDR？**
因为一帧完整的关键帧是 `[SPS][PPS][SEI][IDR slice]`。
锚在 SPS 才能保证 SPS/PPS 和后面的 IDR 一起进同一个 PES ——
接收端拿到第一个包就有了解码器配置。
如果锚在 IDR，SPS/PPS 已经被丢掉了，接收端解不出来。

> 这也是编码时要加 `-x264-params repeat-headers=1` 的原因：
> 让每个关键帧都重复带一遍 SPS/PPS，这样从任意位置接入都能解码。

### pending 的拷贝问题

文件模式下，`pending[]` 存的是**指向内存缓冲的指针**，因为整个文件都在内存里、地址稳定。

实时模式下 **不行**：滚动缓冲会 `memmove`，指针指的内容会变。
所以实时模式必须**把 pending 的 NAL 拷贝出来**：

```c
static unsigned char live_pending_buf[16][8192];
static size_t        live_pending_len[16];
```

两种模式的数据源特性不同，pending 的实现也必须不同。
**这是"抽象泄漏"的典型案例**：接口看起来一样，底层约束不一样。

## ③ 音频：G.711A

### 为什么是 G.711A 而不是 G.711U

| 名称 | SDP PT | 用在哪 |
|---|---|---|
| **G.711A**（PCMA） | **8**（静态） | **中国、欧洲** |
| G.711U（PCMU） | 0（静态） | 美国、日本 |

**GB/T 28181-2016 规定的是 G.711A。**
（注意：第 5 步那个 WebRTC/RTSP 实验用的是 PCMU，那是 RTSP 场景，与国标要求不同。）

两个都是 8kHz 单声道、每样本 1 字节、固定 64 kbps，差别只在压缩曲线：
A-law 对小信号量化更细（适合语音动态范围小的场景），μ-law 反之。

### 帧参数

```
采样率     8000 Hz
帧长       20 ms
每帧样本   8000 × 20 / 1000 = 160 个
每帧字节   160 字节（G.711 是 1 字节/样本）
PTS 步进   90000 × 20 / 1000 = 1800 ticks
```

**注意 PTS 步进和视频不同**（视频 6000，音频 1800），
但**两者都在 90kHz 时钟下** —— 这就是音画同步的基础。

### 音频的 PS 封装

音频帧走的是**同一条 PS/RTP 流**，不是单独开一路 RTP：

```
视频帧:  [Pack Header][System Header][PSM(AV)][PES video]
音频帧:  [Pack Header]                        [PES audio]
```

音频 PES 的差别：

| 字段 | 视频 | 音频 |
|---|---|---|
| `stream_id` | `0xE0` | **`0xC0`** |
| PSM 里的 `stream_type` | `0x1B`（H.264） | **`0x90`**（G.711A） |
| 载荷 | AnnexB H.264 | 160 字节 A-law |

**PSM 必须声明音频那条**（变成 24 字节版本）。
否则接收端按 `sid=0xC0` 去 `psm_fetch` 查不到，
**音频 PES 会被直接丢弃**（见 [06 章](06-MPEG-PS打包器.md)里 ZLMediaKit 的源码分析）。

### 交错策略

真实设备里，视频和音频由各自的采集通道产生，需要"复用"成一条流。
最简单可靠的做法是**按 PTS 排序输出**：

```c
while (running) {
    if (next_video_pts <= next_audio_pts) {
        发视频帧；next_video_pts += 6000;
    } else {
        发音频帧；next_audio_pts += 1800;
    }
}
```

这样输出流里 PES 的顺序就与显示顺序一致。
（本项目为简化，用固定节奏交错；真实设备通常由编码器的复用器统一调度。）

## ④ 代码怎么长出来的

### 媒体源抽象

```c
typedef struct gb_frame_src gb_frame_src_t;

gb_frame_src_t *gb_src_open_file(const char *path);   /* 文件循环 */
gb_frame_src_t *gb_src_open_fifo(const char *path);   /* FIFO 实时 */

/* 返回 >0 帧长；0 暂无数据；-1 结束 */
int gb_src_next_frame(gb_frame_src_t *s, const uint8_t **out, size_t *out_len);
```

**返回 0 而不是阻塞**，是为了让推流线程能同时处理"停止"信号。
如果 `read` 阻塞在里面，BYE 来了也退不出来。

### 与真实 IPC 的对应关系

这是本章最重要的认知：

| 本项目 | 真实 IPC |
|---|---|
| `ffmpeg -f v4l2 ... -f h264 → FIFO` | `Sensor → MIPI → ISP → VENC` 出码流 |
| `gb_src_open_fifo()` 读码流 | 应用层从 VENC 通道取码流（如 `HI_MPI_VENC_GetStream`） |
| `gb_ps_pack_video()` | 应用层打 PS（真机同样要自己做，SoC 不代劳） |
| `gb_rtp_send_ps()` | 应用层发 RTP |

**应用层在真机上做的工作和本项目完全一样** ——
硬件编码器对应用层就是个"出码流的东西"。
差别只在取码流的 API：本项目是 `read(fifo)`，真机是 `HI_MPI_VENC_GetStream()`。

这句话面试时一定要主动说，它直接把"玩具项目"和"真机经验"的差距讲清楚了。

### 音频生成（模拟麦克风）

WSL 里没有声卡，所以本项目用正弦波合成 G.711A：

```c
void gb_audio_gen_init(gb_audio_gen_t *g, int freq_hz, uint64_t start_pts90k);
int  gb_audio_gen_next(gb_audio_gen_t *g, uint8_t *out, size_t cap, uint64_t *pts90k);
```

`gb_audio_gen_next()` 内部：
1. 用相位累加器生成 160 个 `int16_t` 正弦样本
2. 调 `gb_g711a_encode()` 编成 160 字节
3. PTS 累加 1800

**真机上把这一步换成"从声卡/麦克风读 PCM"即可**，
后面的 A-law 编码、PS 封装、RTP 发送完全不用改。
这正是分层的价值。

# 单元测试：A-law 编解码往返误差、帧长

```bash

  -c:v libx264 -preset ultrafast -tune zerolatency -g 30 \
  -threads 1 -x264-params repeat-headers=1:slices=1 \
  -f h264 /tmp/cam.h264.fifo &

./build/gb28181_device -c config.ini -live /tmp/cam.h264.fifo
```

期望日志：

```
[媒体] 实时流模式启动（读 /tmp/cam.h264.fifo，等待 ffmpeg 写入端）
[媒体] FIFO 已连接，流式切帧推流（目标 127.0.0.1:11000，SSRC=...）
[媒体] 实时流已推 10 帧 ...
```

**验证"画面真的在动"的土办法**（原项目用的）：

```bash
# 隔几秒各抓一帧，比较 md5
ffmpeg -y -v error -rtsp_transport tcp -i "rtsp://127.0.0.1:554/rtp/<stream>" \
       -frames:v 1 /tmp/a.jpg
sleep 5
ffmpeg -y -v error -rtsp_transport tcp -i "rtsp://127.0.0.1:554/rtp/<stream>" \
       -frames:v 1 /tmp/b.jpg
md5sum /tmp/a.jpg /tmp/b.jpg      # 两个 md5 不同 = 画面在动
```

**两个 md5 不同**比"我看到画面了"更有说服力 —— 它排除了"卡在某一帧"的可能。

## ⑥ 常见坑

| 坑 | 现象 | 原因 |
|---|---|---|
| `pos < stream_used` 才滚动 | 画面卡住 / 重复数据 | 全消费完时 `stream_used` 没清零 |
| 切分时丢掉 NAL 尾巴 | 每帧花屏（concealing） | 没保留未消费尾部 |
| 锚定在 IDR 而不是 SPS | 首帧解不出来 | SPS/PPS 被丢掉了 |
| pending 存指针但缓冲会 memmove | 偶发花屏 | 实时模式必须拷贝 NAL |
| 音频 PSM 没声明 `0x90/0xC0` | 只有画面没有声音 | `psm_fetch` 查不到 → PES 丢弃 |
| 音频用 PCMU（PT 0） | 平台可能不认 | 国标要求 G.711A（PT 8） |
| 音频 PTS 用了 8kHz 时钟 | 音画不同步 | PTS 必须在 90kHz 域 |
| 音频每帧也带 PSM | 带宽浪费 | 音频只带 Pack Header |

## ⑦ 面试怎么答

**问：实时码流是怎么处理的？**

> "从编码器（或 FIFO）流式读字节，读到的边界是任意的，
> 一个 NAL 单元很可能被切成两半。所以维护一个滚动缓冲：
> 找到一个 NAL 的起始码后，再找下一个起始码来确定它的结尾；
> 如果找不到下一个，说明这个 NAL 还不完整，
> 就把缓冲里未消费的尾部 memmove 到头部，等下一批数据到了再拼。
> 连接开始时还要锚定到 SPS，保证推出去的第一帧带解码器配置。"

**追问：这里有什么坑？**
→ "我们踩过一个边界条件的坑。滚动条件是 `pos > 0` 而不是 `pos < stream_used`。
   看似后者更精确，但漏了一种情况：如果这一轮数据恰好全部消费完，
   `pos == stream_used`，条件不成立就不滚动，`stream_used` 不清零，
   下一轮新数据追加在旧数据后面 → 旧数据被重复推 → 画面卡住。"

**追问：音频怎么做的？**
→ "G.711A，国标规定的。8kHz 单声道，20 毫秒一帧 160 字节。
   音频不单独开 RTP 流，而是打成 PES 和视频复用在同一条 PS 里 ——
   stream_id 用 0xC0，PSM 里对应声明 stream_type 0x90。
   关键是音频 PTS 也必须走 90kHz 时钟，步进 1800，
   这样它和视频 6000 的步进在同一个时间轴上，音画同步天然成立。"

**追问：你这套和真机差在哪？**
→ "应用层的工作完全一样：拿码流、打 PS、发 RTP。
   差别只在取码流的接口 —— 这里是 read FIFO，
   真机上是调用 SoC 的 VENC 出流接口（比如海思的 HI_MPI_VENC_GetStream）。
   硬件编码器对应用层是黑盒。所以这套代码验证的软件栈和真机固件里那一层是等价的。"
