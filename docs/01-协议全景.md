# 01 协议全景：GB28181 在 IPC 里的位置

> **一句话**：GB28181 是一套"让摄像机主动注册到平台、等平台来点播"的国标协议。
> 它的信令走 SIP，媒体走 RTP，中间用 MPEG-PS 把音视频装进同一条流。

---

## ① 这一步解决什么问题

你手上有一台摄像机，一个监控平台。平台怎么知道这台摄像机存在？怎么看到它的画面？

有三种常见答案，GB28181 是第三种：

| 方案 | 谁主动 | 典型场景 | 缺点 |
|---|---|---|---|
| **RTSP 直连** | 播放器主动连设备 | 局域网调试、NVR 直连 | 平台必须先知道设备 IP；NAT 后面连不上 |
| **ONVIF** | 双方都有：设备可被发现，也可注册 | 国际通用、海康大华都支持 | 规范庞杂；只管设备管理，媒体还是走 RTSP |
| **GB28181** | **设备主动注册** | 中国公安/安防行业标准 | 国标专用；非中国项目基本不用 |

**"设备主动注册"是理解 GB28181 的钥匙。**

设备在 NAT 后面、IP 会变，平台不可能主动找到它。所以国标反过来：
设备开机就往平台发 `REGISTER`，告诉平台"我在这个地址，我叫这个编号"，
之后每隔 60 秒发一次 `Keepalive` 心跳。平台要画面时，向下发 `INVITE`，
设备回一个 `200 OK` 并在里面写清"你把 RTP 发到我这个端口"，
然后设备开始推流。

这套"注册制"直接决定了代码结构：**设备端是一个被动响应者**，
只有一个主循环在收 UDP 包，收到什么处理什么，而不是自己去找平台。

## ② 协议长什么样

### 一台 IPC 内部的数据流

```
   Sensor ──MIPI──> ISP ──> VI ──> VPSS ──┬──> VENC(硬件编码器) ──> H.264/H.265 码流
                                          └──> (AI 分支) NNIE
                                                  │
                                    ┌─────────────┘
                                    ▼
                        ┌───────────────────────┐
                        │  应用层（本项目教的）   │
                        │  1. 按 NAL 切帧        │
                        │  2. 打 MPEG-PS        │
                        │  3. 切 RTP 包         │
                        │  4. UDP 发出去         │
                        └───────────────────────┘
```

**只有最后这个方框是本项目在做的。** 前面那些（ISP 3A、降噪、WDR、VENC 调用）
是 SoC 厂商 SDK 的活（海思 HiSilicon 的 `HI_MPI_VENC_*`、瑞芯微的 RKMPP 等）。

这个分工极其重要，面试时必须主动说：
> "我做的是设备端应用层：拿编码器输出的码流，做 PS 封装和 RTP 发送。
>  真机上 ISP 和硬编对应用层是黑盒，通过 SDK 出流。"

### 三层协议栈

```
    平台包（wvp-pro）                        设备（本项目）
 ┌──────────────────┐                    ┌──────────────────┐
 │   SIP 信令服务    │◄──── SIP/UDP ─────►│                  │
 │  (Java/Spring)   │     5060 / 5061    │   gb_sip.c       │
 └──────────────────┘                    │   gb_manscdp.c   │
                                          │                  │
 ┌──────────────────┐                    │   gb_ps.c        │
 │  流媒体服务       │◄── RTP/UDP 11000 ──│   gb_rtp.c       │
 │  (ZLMediaKit)    │   载荷 = MPEG-PS   │   gb_media.c     │
 └──────────────────┘                    └──────────────────┘
        │
        ▼ 分发
   RTSP / RTMP / HLS / HTTP-FLV  →  播放器
```

**注意平台侧是两个独立组件**：SIP 信令服务（wvp-pro）和流媒体服务（ZLMediaKit）。
它们不合并，因为职责完全不同：一个管"谁在哪、要不要流"，一个管"流从哪来、往哪去"。
[SIP REGISTER 成功后，wvp-pro 只是把设备信息写进数据库；
真正收 RTP 的是 ZLMediaKit。](02-环境搭建.md)

## ③ 为什么是 PS，不是"两路 RTP"

这是本章最重要的一节。WebRTC 的做法是：视频一路 RTP、音频一路 RTP，
同步靠 RTCP SR 报文把 RTP 时间戳映射到 NTP 墙上时钟。

**GB28181 不这么做。** 它把音视频先装进一个 MPEG-2 Program Stream 容器，
再整条塞进一路 RTP。三个原因：

**原因一：音画同步变成"免费"的。**
PS 容器里的每个 PES 包都带 33 位 PTS，而这些 PTS 来自**同一个 90kHz 系统时钟**。
接收端只要解析 PS，就同时拿到了视频第 3 秒和音频第 3 秒 —— 因为它们用的是同一条时间轴。
不需要 RTCP、不需要 NTP 对时。

> 这一条直接回答 JD 里"音画不同步怎么排查"：在 GB28181 里，
> 音画同步的依据就是 PS 里的 PTS，不同步第一件事是查 PTS 有没有写错、有没有同源。

**原因二：单端口复用，穿透友好。**
国标设备端只开一个 UDP 收流口（如 11000），所有媒体从这一个口进出。
不用在 NAT 上开一堆端口。

**原因三：兼容存量。**
安防行业大量存量设备和平台基于 MPEG-PS。国标要能接入存量生态。

**代价**：PS 头部开销不小（每帧 50 字节左右），比纯 RTP 传输效率低。
但对 2Mbps 的监控码流来说可以忽略。

## ④ 代码怎么长出来的

本项目里，三层各对应一组文件：

| 层 | 文件 | 关键函数 |
|---|---|---|
| 信令 | `gb_sip.c` | `gb_sip_register()`、`gb_sip_build_200()` |
| XML | `gb_manscdp.c` | `gb_xml_catalog_response()` |
| 容器 | `gb_ps.c` | `gb_ps_pack_video()`、`gb_ps_encode_pts()` |
| 传输 | `gb_rtp.c` | `gb_rtp_slice()`、`gb_rtp_pack()` |
| 装配 | `gb_media.c` `main.c` | `gb_push_loop()` |

**关键设计：字节层与 IO 层严格分离。**
`gb_ps.c` / `gb_rtp.c` / `gb_md5.c` / `gb_g711.c` 全都是纯函数 ——
不碰 socket、不碰文件、不依赖全局状态。
所以它们能被单元测试逐字节断言，也能单独放进 kata 里跑。

（这条不是洁癖，是排障需求：当 ZLMediaKit 说"收流超时"时，
你需要能在 3 秒内区分"是 PS 字节错了"还是"是网络没通"。
纯函数可以离线反复验证，带 IO 的不能。）

## ⑤ 怎么验证你理解了

不用跑代码，先回答三个问题：

1. 平台为什么会主动给设备发 `INVITE`，设备怎么知道往哪推流？
2. 如果 GB28181 改成视频音频各一路 RTP，音画同步要多做什么？
3. 为什么设备端不需要"去找平台"？

<details>
<summary>参考答案</summary>

1. 因为设备先 `REGISTER` 注册过，平台知道它在哪、叫什么。设备往哪推流由平台的
   `INVITE` 消息里的 **SDP** 决定：`c=IN IP4 <IP>` 给目标地址，`m=video <port>` 给端口，
   `y=<SSRC>` 给同步源标识。

2. 要额外实现：两路 RTP 各自的时间戳域、RTCP SR 报文（把 RTP 时间戳映射到 NTP 墙上时钟）、
   接收端的时间轴对齐算法、以及抖动缓冲的联合调度。这就是 WebRTC 干的事。

3. 因为国标是注册制：设备绑定到固定平台地址，开机就注册，之后被动响应。
   设备不需要"发现"平台，地址是配置里写死的（`server_ip` / `server_port`）。

</details>

## ⑥ 常见坑

| 坑 | 现象 | 原因 |
|---|---|---|
| 把 wvp-pro 当成流媒体服务器 | 注册成功但没画面 | wvp-pro 只发信令，RTP 由 ZLMediaKit 收 |
| 以为设备要主动连流媒体服务器 | 不知道往哪推 | 推流地址由 `INVITE` 的 SDP 给，不是配置里的 |
| 拿 ONVIF 的思路找 GB28181 | 找不到"发现设备"的步骤 | 国标没有发现协议，只有注册 |
| 以为 PS 只是"打包格式" | 说不清为什么非用不可 | PS 的真正价值是共享时间基 → 音画同步免实现 |

## ⑦ 面试怎么答

**问：介绍一下这个 GB28181 项目。**

> "我做的是设备端（IPC 侧）的协议实现。整体分三层：
> SIP 信令负责注册、心跳、目录上报和点播响应；
> 媒体面用 MPEG-PS 把 H.264 和 G.711A 音频装进同一条流 —— 这样音视频天然共享
> 90kHz 时间基，音画同步不需要额外做 RTCP 对时；
> 最外层是 RTP over UDP，一帧 PS 按 MTU 切片，靠 marker 位标记帧结束。
>
> 应用层只负责拿编码器输出的码流做封装和发送，ISP 和硬件编码器通过 SoC SDK 出流，
> 对应用层是黑盒。"

**追问：为什么不用两路 RTP 分别传音视频？**
→ 用上面"原因一"回答，并补一句"两路 RTP 就是 WebRTC 的做法，需要 RTCP SR 做时间轴映射"。

**追问：PS 会不会有性能问题？**
→ 承认头部开销（每帧约 50 字节），说明对 2Mbps 监控码流可忽略；
   并补充"真实瓶颈在硬件编码器和网络，不在 PS 封装"。
